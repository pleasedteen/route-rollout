# 本地转发服务的安全批量发布工具

在维护窗口里给一组**本地转发服务**更新路由。同一批可能只切成功几台，发布进程也
可能在服务已经切换后丢掉确认。本项目提供：

- 可独立运行、重启后保留生效配置的**本地转发服务**（标准库 HTTP 控制面）；
- 一个**发布工具**：先出满足约束的完整计划，再分批切换，支持查状态、暂停、继续、
  回退、进程崩溃后由新进程接手；
- **故障夹具代理**：复现部分生效、确认丢失、丢请求、延迟投递、失联、抖动；
- 本地拓扑样例与一条 80 秒内跑完的测试命令（实测约 30 秒）。

只依赖 Python 3.11 标准库，无需安装第三方包。所有进程都以 `python3 -I`（隔离模式，
不读当前目录/环境变量，避免被同目录恶意模块劫持）启动。

## 2. 核心模型与安全语义

一台服务对每个**流量类别**保存一条下一跳规则：

- 转发到下游服务：`{"next_hop": "relay1"}`
- 本节点就是该类流量的**固定出口**：`{"local_egress": true}`

整套规则 `{class: rule}` 经规范化后算 SHA-256 得到**版本指纹**（`version_token`）。
规则内容相同则指纹相同——这是 apply 幂等和"按实际生效版本对账"的基础。

### 规划的安全定义（发布与回退共用）

设批次依次为 B1..Bm。对任意批次 Bi 和它的**任意子集 S（含空集与全集）**，
"前 i-1 批已整体生效、Bi 中恰好 S 已生效"的混合状态下，从任一节点、任一类流量
出发，都必须无环并到达该类别的固定出口。规划器枚举每个批次的全部子集逐一校验，
因此**同批服务按任意顺序生效、中途只切了一部分，路由始终可达**。

规划器用回溯搜索满足 `单批服务数 ≤ max_batch_size`、`总批数 ≤ max_batches`
的划分；无解时放松批数上限求出最少批数，并附一个具体的可达性破坏点（如环路）
作为可读原因，**此时不创建任何发布状态、不触碰服务**。

### 进度与权威状态

发布进程**不持有权威状态**。权威状态只有两处：

1. 状态文件 `release.json`（原子写 + 跨进程 `flock`）：阶段、批次进度、计划、
   已观察到的版本、栅栏代数（`epoch`）、**未决操作**（`pending`）、暂停代数；
2. 各服务 `/status` 返回的**实际生效版本**（服务本地原子持久化）。

每个推进周期先 `reconcile`：查所有服务的实际版本并据此纠正本地进度、结算已
可见生效的未决操作，再决定是否下发。因此即使上一个进程崩溃、确认丢失，新进程
只凭状态文件 + 服务实际版本就能正确接手。apply 按规则指纹幂等，重发安全。

### 栅栏代数与未决操作（防"迟到/重发覆盖"）

只靠"重发安全"还不够：一个迟迟才到的正向 apply 仍可能在暂停或回退之后落地，
把已经确定的回退结果翻回去。为此引入**栅栏代数**：

- 每次下发前，先在状态文件里把操作登记为 `pending` 并分配一个**单调递增**的
  `epoch`（分配时下界取服务端已见到的最大栅栏，保证跨发布也单调）；
- apply/fence 携带 `epoch`，服务记住见过的最大值并持久化；任何 `epoch` 更小的
  apply 一律 `409` 拒绝、**不改配置**；
- 暂停一经接受（原子写 `PAUSED` + 抬高 `epoch`），任何进程都无法再登记新操作，
  也就不可能开启新批次；随后给每个节点装栅栏，使在途请求"要么已生效、要么被
  永久拒止"，二者都是确定结果；超时则保留 `pending`，`status` 可查。
- 回退前同样**无条件**给所有节点装更高栅栏（否则"本来就已是老版本、无需 apply"
  的节点没有更大代数，迟到请求仍能把它翻回新配置），再按各节点**实际**规则规划。

阶段机：`RUNNING → PAUSED → FORWARD_COMPLETE → ROLLING_BACK → ROLLED_BACK`，
连续不可达时进入 `FAILED`（配置不被破坏，恢复后 `resume` 即可）。回退只在
`FORWARD_COMPLETE` 或 `PAUSED` 之后才规划。

## 3. 快速开始

### 一条命令跑全部测试（约 30 秒，要求 80 秒内）

```bash
cd route-release
bash run_demo.sh
```

输出形如：

```
########## 第一部分: 规划器/模型单元测试 ##########
  PASS  发布前配置合法
  ...
单元测试全部通过
########## 第二部分: 安全语义验收(延迟投递/丢确认/进程接手/暂停/回退) ##########
场景 A: 延迟投递 + 暂停(卡在代理里的正向 apply)
场景 C: 丢确认 + 进程接手(apply 在途时 kill -9)
...
结果: 28 PASS / 0 FAIL   用时 14.7s (上限 80s)
########## 第三部分: 端到端故障演练(真实本地进程) ##########
...
结果: 22 PASS / 0 FAIL
```

验收部分（`tests/acceptance.py`）用夹具**逐条验收**：

- **延迟投递**：让 apply 被代理扣住若干秒，在它仍在途时 `pause`——暂停不得提前
  报完成，必须等该请求"生效或永久拒止"，返回后迟到请求不得改写版本；
- **丢确认**：apply 实际生效但响应被吞，发布进程在途中被 `kill -9`，新进程接手
  未决操作，按服务实际版本收尾；
- **进程接手**：并行 CLI 在暂停后无法登记新操作（不开新批），暂停幂等；
- **回退**：只在暂停/完成后按各节点实际混合规则规划，满足单批规模上限；重放旧
  代数的正向请求被栅栏 `409` 拒绝、不覆盖回退结果；
- **超时未决可查**：节点失联使暂停等待超时后，未决操作仍保留并可由 `status` 查到。

端到端演练覆盖：无解规划、部分生效后 `kill -9`、新进程接手、确认丢失对账、
逐跳可达性验证、暂停/继续、服务重启保留配置、完成后回退。

### 手动拉起拓扑

```bash
# 拉起 7 台服务; edge2/edge4 额外挂故障代理
bash bin/start_topology.sh .manual-workdir

# 用完清理
python3 -I bin/runmod.py route_release.launcher down --workdir .manual-workdir
```

工作目录下生成：`registry.json`（节点→控制面 URL）、`state/`（各服务持久化规则）、
`proxy/`（故障配置，可在线改写）、`logs/`、`pids.json`。

## 4. 发布操作手册

以下用 `WD=.manual-workdir` 表示拓扑工作目录。

### 4.1 提交计划（动配置前先看完整计划）

```bash
python3 -I bin/runmod.py route_release.publisher submit \
  --topology ../examples/topology.json \
  --old-rules ../examples/old_rules.json \
  --new-rules ../examples/new_rules.json \
  --registry $WD/registry.json \
  --state $WD/release.json \
  --max-batch-size 2 --max-batches 4
```

先打印完整批次计划与上限核对结果，再落状态文件。无解时退出码 2 并说明原因，
原配置保留。

### 4.2 发布 / 继续 / 暂停

```bash
python3 -I bin/runmod.py route_release.publisher run    --state $WD/release.json
python3 -I bin/runmod.py route_release.publisher pause  --state $WD/release.json
python3 -I bin/runmod.py route_release.publisher resume --state $WD/release.json
```

- `run` 可反复执行；进程崩溃后直接再次 `run` 或 `resume`，会先对账再续跑。
- `pause` 一接受就不再开启任何新操作/新批次；随后给所有节点装栅栏，等每个在途
  操作"已生效"或"被更高栅栏永久拒止"（二者都是确定结果）后保留进度返回。
  等待超时则以非零退出，未决状态保留（`status` 可见），可再次 `pause` 或直接
  `resume`。
- `resume` 从保留的进度继续；`FAILED` 也用它恢复。

### 4.3 查状态与实时验证

```bash
python3 -I bin/runmod.py route_release.publisher status --state $WD/release.json
python3 -I bin/runmod.py route_release.publisher verify --state $WD/release.json
```

`status` 列出每台服务的**实际生效版本**、发布前/目标指纹、批次进度、栅栏代数，
以及**未决操作**（已发出未确认：节点、代数、目标、方向、起始时间）。
`verify` 从每个节点、每类流量发起**真实逐跳转发探测**（服务间互相 HTTP 调用，
带环路检测），确认都到达固定出口。

### 4.4 回退到发布前配置

只在**正向发布完成**或**暂停完成**后允许回退（正向未完成时直接拒绝，避免拿不确定
的现场做规划）：

```bash
python3 -I bin/runmod.py route_release.publisher rollback --state $WD/release.json
```

回退前会先给所有节点装更高栅栏，让任何在途/迟到的正向请求都不可能再生效；再
**以服务当前实际生效配置（可能是新老混合）为起点重新规划**，同样枚举任意部分
生效子集的可达性、受单批规模与总批数上限约束；无解则不动配置并说明原因。默认沿用
正向发布的两项上限，也可用 `--max-batch-size/--max-batches` 覆盖。回退中断后续跑
时会先校验既有计划与真实现场是否一致，不一致则按实际重新规划。

## 5. 转发服务接口

每台服务独立监听一个本地端口（注册表 `registry.json`）：

| 方法 | 路径 | 作用 |
| --- | --- | --- |
| GET  | `/status`   | 返回节点名、生效版本指纹、栅栏代数、各类流量下一跳 |
| POST | `/apply`    | 整套切换本机规则；内容相同则幂等返回 `duplicate:true`；`epoch` 低于栅栏则 `409 stale` 拒绝 |
| POST | `/fence`    | 抬高栅栏代数，让更早代数的 apply 永久失效（暂停/回退的确定性来源） |
| POST | `/probe`    | 从本节点逐跳真实转发某类流量，返回完整路径与出口 |
| POST | `/shutdown` | 测试/演示收尾 |

生效规则与栅栏代数通过"临时文件 + `os.replace`"原子落盘到 `state/<node>.json`，
进程重启后自动恢复（见端到端场景 7）。

## 6. 故障夹具

代理配置在 `$WD/proxy/<node>.json`，**在线改写即生效**（代理按文件 mtime 热加载）。
故障只作用于变更操作 `POST /apply`；`/status`、`/fence` 放行——这正是
"确认丢失但仍能查到真实生效状态、并装上栅栏"的前提。

| 配置 | 行为 |
| --- | --- |
| `mode: pass` | 全放行 |
| `mode: drop_confirm` | 转发给服务并执行成功，但吞掉响应（发布方连接被断开） |
| `mode: drop_request` | 直接丢弃请求，服务根本不知道这次切换 |
| `mode: flaky` | 前 `fail_times` 次返回 503，之后自愈 |
| `delay_sec` / `delay_times` | 转发前先等待若干秒，复现"延迟投递/在途请求"（`delay_times` 次后不再延迟） |
| `blackhole: true` | 所有请求（含 `/status`、`/fence`）都不转发，等效节点失联 |

所有故障模式都遵守配额（注入这么多次后自动恢复）。发布工具对 apply 做有限退避
重试，每次重试前先查实际状态，借助幂等与栅栏保证重发安全。

把某台服务接入代理：启动拓扑时加 `--proxy-node <node>`（可重复）。

## 7. 关键设计取舍

- **为什么枚举子集而不是只校验整批前后两个状态？** 同一批只切成功几台是常态，
  只校验端点状态无法发现"切了一半成环"。枚举全部子集才能保证任意顺序、任意
  部分生效都可达。
- **为什么 apply 要幂等、且以服务实际版本为准？** 确认丢失时发布方无法区分
  "没生效"和"生效了但没回执"。内容指纹让重发无副作用，对账让进度以服务为准，
  新进程才能无损接手。
- **为什么还要栅栏代数？** 幂等只能保证"重发不重复破坏"，却挡不住一个迟迟才
  到的旧 apply 在暂停/回退之后落地，把已确定的结果翻回去。单调递增的 epoch +
  服务端记住最大值，让"迟到/重发"的旧意图被永久拒止。
- **为什么每次下发前要先把未决操作落盘？** 进程可能在 HTTP 发出到确认之间的
  任何一刻崩溃。先把 `pending(epoch, 目标, 方向)` 写进状态文件，新进程才能知道
  "有操作在途、代数是多少、目标是什么"，据实际生效结果收尾，而不是蒙查。
- **为什么暂停要等"生效或永久拒止"而不是只看版本？** 请求可能仍在代理里没到
  达服务；此时版本当然是老指纹，按版本判断会误报"暂停完成"，随后该请求落地就
  改写了结果。装上更高栅栏后，再查到的版本就是不会被改写的最终结果。
- **为什么回退要基于实际混合状态重新规划？** 暂停/崩溃后各节点版本可能新老不一，
  从纯目标配置规划出的批次未必覆盖真实的混合起点。
